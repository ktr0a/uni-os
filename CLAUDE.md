## Claude Code notes

The line above imports [AGENTS.md](AGENTS.md), which holds every instruction for this repo. These notes only add Claude Code specifics; nothing essential lives here. Claude Code is the only agent Uni OS has been tested with (desktop app, CLI and Remote Control).

- **Permission mode in this repo.** Work in a mode where the student sees each step (ask, or accept edits): setup writes into their vault and changes their system. Bypass permissions belong on the always-on host (module `vm`), where unattended jobs need them and the blast radius is the vault and a replaceable box. On the laptop, desktop scheduled tasks keep the permission mode of the session that created them, so they run unattended only when created from a bypass-mode session. That is a choice the playbook asks the student about (`agent.permission_posture`, default `accept-edits`), never something you switch on yourself.
- **Skills.** Each module's skills render to `<vault>/_agent/skills/<id>/SKILL.md`. Setup links or copies them into `agent.skills_dir` (default `.claude/skills`, relative to the vault), so sessions opened on the vault find them. On Google Drive for desktop, copy them: links inside a synced vault fail. Copy them again after each `render`. Details: [docs/agents.md](docs/agents.md).
- **Scheduled tasks.** Laptop jobs become desktop-app scheduled tasks. The setup agent creates one task per cron line with the scheduled-task tool, using the output of `modules/scheduler-local/scripts/list_jobs.py` (`cron <job>` and `prompt <job> --session app`). Tasks run only while the app is open, can start a few minutes late, and catch up missed slots after wake-up; every job prompt guards against that. Details: [modules/scheduler-local/README.md](modules/scheduler-local/README.md).
- **Remote Control.** On the always-on host, `rc-loop` keeps a Remote Control server running in the vault, so the student can open sessions from the phone. Interactive jobs (`SESSION="rc"`, for example the check-in) open a Remote Control session and push its link. Every new Remote Control session notifies the phone, so jobs that ask nothing run headless. Details: [modules/vm/README.md](modules/vm/README.md).
- **Subagents.** Use them for bulk reading: the module READMEs, long PDFs, a survey of the catalogue. Keep the main context small and write findings to files. In a vault, `agent.max_helpers` (default 2) caps how many run at once.
- **Hooks.** The always-on host uses a `UserPromptSubmit` hook (a fixed re-read nudge when the rules or a role brief changed) and a `Stop` hook (marks the end of an interactive job's first turn). A rewritten `settings.json` reaches running sessions, so change settings only with a yes.
- **Messages between sessions.** ListAgents and SendMessage reach sessions on the laptop and on the host, addressed by title. A message to a laptop session in another permission mode waits for approval. Cloud sessions can't be messaged reliably; use the inbox update notes of module `inbox-sync` instead.
- **Cloud sessions** need a git repository, can't run in bypass mode and can't read laptop files. They suit course roles, not the setup.
- **Pushes.** Claude Code's own push notification is held back while the student counts as active (always, on a headless host), so Uni OS sends pushes through ntfy and the push gate (`uni-os push`).
- **Usage.** `modules/roles/scripts/usage_map.py` reads the local transcripts (`$CLAUDE_CONFIG_DIR/projects` or `~/.claude/projects`) and shows which sessions use the most. It is read-only.
